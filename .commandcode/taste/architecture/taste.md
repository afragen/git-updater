# Architecture
- Avoid adding memoization/caching layers (e.g., memoized whole-set projection maps with per-write invalidation) to eliminate queries that are already cheap indexed lookups (e.g., `WHERE slug = %s` on a UNIQUE key): at realistic data sizes the savings are negligible (single-digit ms/page load) and the stale-cache invalidation complexity across every write path is not worth it — prefer keeping the simple direct-query code. Confidence: 0.80
- When optimizing hot-path reads that hit the DB on every projected/single-column call, the user explicitly prefers backing them with a parallel WordPress object-cache layer (e.g., `wp_cache_get`/`wp_cache_set` under the existing `'git-updater'` group) rather than converting the projected reads into full-row reads that would change the DB row-cache/memoization semantics — the explicit constraint was "We don't want to turn them into full-row reads." Keep the DB `$row_cache` semantics untouched and add object cache as an independent, timeout-validated layer. Confidence: 0.60
- Persistent object-cache invalidation must NOT rely on a per-request instance property that records the written keys: the tracking array lives only for the current PHP request, so a write in a later request cannot delete object-cache keys a prior request populated — on a persistent cache (Redis/Memcached) this leaves stale projections and a stale timeout warm for up to their row timeout, a correctness regression the in-request `$row_cache` never had. Cross-request-safe invalidation needs a per-slug generation/epoch embedded in the key (bumped on every write) or a stored per-slug keyset, not per-request tracking. The user surfaced this concern by asking whether the caching change was "no longer safe," expecting the assistant to audit every read/write/invalidation path and confirm the failure mode rather than defend the change. Confidence: 0.70
- When an object-cache layer must run on servers WITHOUT a persistent cache (the default non-persistent `WP_Object_Cache`, or an unavailable/misbehaving backend), it must degrade gracefully and never worsen correctness or availability: the DB is always authoritative, `wp_cache_*` is treated as a pure accelerator that never throws (every miss/`false` falls through to the existing DB query), and correctness must not depend on persistence. On a non-persistent cache the generation counter restarts each request (reads seed gen=1, writes bump to gen=2 within the request) so there is no cross-request state to invalidate and nothing can go stale; per-request dedupe (via `$row_cache` + per-request object cache) still works. TTL is an optimization, not the correctness mechanism — the default cache ignores `$expire`, so rely on the generation bump (not TTL) for correctness; never store with TTL <= 0. The only thing a non-persistent host loses is the cross-request speedup, which is the intended safe degradation. This requirement was explicitly raised during plan review ("ensure graceful degradation on servers without persistent object caching"). Confidence: 0.80
- Prefer isolating a caching subsystem (e.g., the object-cache/projection tier) into its own dedicated single-responsibility class rather than embedding it in the DB-table class — this centralizes the safety invariant (cross-request invalidation, graceful degradation) and makes the tier unit-testable in isolation. The user explicitly requested isolating the object-cache tier into its own class during the caching redesign. Confidence: 0.60
- When upgrading custom database table schemas, prefer a schema-versioned non-destructive migration over drop-and-recreate or blind dbDelta: keep a `SCHEMA_VERSION` constant independent of the plugin version, run dbDelta on upgrade, then verify every expected column actually exists (e.g., via DESCRIBE against the canonical column whitelist plus key columns) and only fall back to drop-and-recreate if dbDelta genuinely failed — the migration preserves the table structure despite dbDelta's unreliable column-add behavior. Confidence: 0.70
- Clearing cached repo data so it re-collects is intentional and desired on ANY package upgrade — the plugin's own upgrade AND individual plugin or theme package updates — not only the plugin-wide upgrade path: the user clarified "It's not only a plugin upgrade but a package upgrade, plugin or theme," and the stated purpose of the GU_Upgrade clear is "that all repo data that is obtained via API request is removed so another API request may occur" (re-fetch with the new version). Design cache-clear methods (e.g., `delete_all_api_data()` for all repos and `delete_repo_api_data($slug)` for a single package) by classifying each column as API-derived/re-collectable (readme, tags, meta, release assets, error backoff, and re-derivable values like `primary_branch` — re-detected on the next parse) vs. genuine user/local state (`current_branch`, the user's active branch selection) — clear the former, preserve the latter at both the all-repos and per-package flush levels (e.g., the flush-repo-cache endpoint), rather than doing a full table wipe or removing the clear entirely. Confidence: 0.85

- Prefer optional/opt-in features over mandatory ones, especially for security configurations. Confidence: 0.70

- Prefer custom database tables over the WordPress options table for storing repository data/metadata (headers, API responses, branches, cache, error state), with indexing on the repository slug; reserve `update_site_option`/options for general data only (settings, credentials/tokens, API keys, config lists). The user explicitly stated this split as a project invariant — "ensure all repository data is stored in tables and update_site_option only used for general data" — and treats any leftover repo-data option write (e.g., a legacy `current_branch_<slug>` key) as a migration violation to eliminate, even when it's only read by tests. The user actively follows up an audit that flags such a leftover with "add recommended change and test" to get the migration implemented. Confidence: 0.88

- To test whether background/completed work is done (e.g., `waiting_for_background_update()`), check the actual completion bookkeeping (the `ran` key written after a full fetch cycle) rather than cache emptiness — `empty($cache)` conflates "not yet run" with "cache cleared/expired/partial failed fetch".
