# Architecture
- Avoid adding WordPress filters for simple configuration values like TTL unless explicitly requested. Confidence: 0.70
- Prefer optional/opt-in features over mandatory ones, especially for security configurations. Confidence: 0.70
- Prefer server-side configuration over client-side configuration when the server is the source of truth (e.g., domain validation, access control). Confidence: 0.75
- Public repositories should bypass domain validation entirely. Confidence: 0.75
- Use subsystem-specific prefixes for WordPress filters/hooks (e.g., `git_updater_lite_` instead of `git_updater_`) to isolate functionality and prevent unintended side effects on other parts of the codebase. Confidence: 0.70
- Prefers the `git_updater_` function prefix over `fragen_git_updater_` in the Git Updater satellite API plugin repos (gist, bitbucket, gitea, gitlab) — explicitly renamed the custom autoloader function `fragen_git_updater_register_autoloader()` → `git_updater_register_autoloader()` across all four repos. Confidence: 0.80
- In Git Updater, `private_package` in Additions blocks API access entirely (not sharable); it does NOT indicate whether the repository is private on the git host. Use existing repo metadata from cached API data (not plugin/theme headers) for detection instead. Confidence: 0.85
- When the system already stores relevant metadata, use it directly for feature targeting rather than introducing heuristic detection (e.g., composer.json parsing, auth token presence). Confidence: 0.75
- Place new classes directly in their main namespace directory (e.g., src/Git_Updater/Lite_Domains.php) rather than creating new subdirectories (e.g., src/Git_Updater/Settings/Lite_Domains.php) unless the class is part of an existing sub-module like Additions. Confidence: 0.65
- Prefer custom database tables over the WordPress options table for storing repository data/metadata, with indexing on the repository slug. Confidence: 0.70
- Git Updater is a multi-repo ecosystem: the main `git-updater` repo plus per-provider satellite plugin repos (git-updater-bitbucket, -gist, -gitea, -gitlab, -lite, -oauth-connector) cloned side-by-side locally. Satellite API classes live in the `Fragen\Git_Updater\API` namespace and extend the main repo's `API` base class. Confidence: 0.85
- Do NOT declare `afragen/git-updater` as a composer dependency in satellite API plugin repos: it pulls heavy transitive deps (notably freemius) into `vendor/`, and the committed autoloader then fatals referencing the absent `freemius/wordpress-sdk/start.php` (git-updater's `exclude-from-files` only applies when it is the root package). The user explicitly does not want git-updater's dependencies committed to the API plugin repos. Confidence: 0.90
- For satellite-repo CI tests, load the main repo's base `API` class without Composer (preferred direction: a manual PSR-4 autoloader in `tests/bootstrap.php` pointing at a sibling git-updater checkout, plus a CI checkout step) and `require-dev` only the minimal lightweight packages the API class graph actually needs (`afragen/singleton`, `erusev/parsedown`, `afragen/wp-readme-parser`). Confidence: 0.70
- The custom PSR-4 autoloader file `autoloader.php` (defining `git_updater_register_autoloader()`) now exists and is byte-identical across all four satellite API plugin repos — git-updater-gist, -bitbucket, -gitlab, and -gitea — not only git-updater-gist. When asked to fix WPCS or other issues in "the autoloader" of the API plugins, apply the change to all four and verify each with `vendor/bin/phpcs` (and `vendor/bin/phpcbf` for auto-fixable alignment). Confidence: 0.85
- After a side-effectful operation that may modify shared persistent state (e.g., `delete_token()` calling `update_site_option()`), re-read from the canonical storage (e.g., `get_site_option()`) to decide subsequent behavior rather than trusting in-memory local variables that may be stale. Confidence: 0.75
- Gate optional/polish notifications (e.g., empty-token reminder emails) to premium license holders via `gu_fs()->can_use_premium_code()`, guarded with `function_exists('gu_fs')` for cron/CLI contexts where Freemius may not be booted; core failure notifications go to all users. Confidence: 0.75
- Condition persistent admin notices on the user-facing UI state (e.g., the Connect button displays whenever the provider token is empty) in addition to internal flags, so the notice and the UI never disagree even when the token is emptied outside a refresh failure. Confidence: 0.70
- In Git Updater's dev channel / `can_update_repo` logic, the actual remote version takes precedence over a dev release asset version when they differ (e.g., dev asset key `3.0.0-beta1` vs. remote `2.0.0` → `2.0.0` is used; nightly keys like `23.8-nightly` never override the real remote version). Dev release asset keys only matter when they match the remote version. This logic is mirrored across GU_Trait and REST_API.php, so keep it consistent. Confidence: 0.70
- Determine which OAuth providers are "running"/active via the canonical `get_running_git_servers()` list (GitHub always included; companion API plugins register themselves through the `gu_running_git_servers` filter when active) for features like cron reminders and admin notices, rather than hardcoding plugin file names with `is_plugin_active()` checks. Confidence: 0.65
