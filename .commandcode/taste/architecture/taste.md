# Architecture
- Avoid adding memoization/caching layers (e.g., memoized whole-set projection maps with per-write invalidation) to eliminate queries that are already cheap indexed lookups (e.g., `WHERE slug = %s` on a UNIQUE key): at realistic data sizes the savings are negligible (single-digit ms/page load) and the stale-cache invalidation complexity across every write path is not worth it — prefer keeping the simple direct-query code. Confidence: 0.8
- When upgrading custom database table schemas, prefer a schema-versioned non-destructive migration over drop-and-recreate or blind dbDelta: keep a `SCHEMA_VERSION` constant independent of the plugin version, run dbDelta on upgrade, then verify every expected column actually exists (e.g., via DESCRIBE against the canonical column whitelist plus key columns) and only fall back to drop-and-recreate if dbDelta genuinely failed — the migration preserves the table structure despite dbDelta's unreliable column-add behavior. Confidence: 0.7
- Clearing cached repo data so it re-collects is intentional and desired on ANY package upgrade — the plugin's own upgrade AND individual plugin or theme package updates — not only the plugin-wide upgrade path: the user clarified "It's not only a plugin upgrade but a package upgrade, plugin or theme," and the stated purpose of the GU_Upgrade clear is "that all repo data that is obtained via API request is removed so another API request may occur" (re-fetch with the new version). Design cache-clear methods (e.g., `delete_all_api_data()` for all repos and `delete_repo_api_data($slug)` for a single package) by classifying each column as API-derived/re-collectable (readme, tags, meta, release assets, error backoff, and re-derivable values like `primary_branch` — re-detected on the next parse) vs. genuine user/local state (`current_branch`, the user's active branch selection) — clear the former, preserve the latter at both the all-repos and per-package flush levels (e.g., the flush-repo-cache endpoint), rather than doing a full table wipe or removing the clear entirely. Confidence: 0.85

- When a boolean decision method has multiple inputs, prefer returning the boolean expression directly (e.g., `return (bool) $a && ! empty( $b ) && $c;`) instead of assigning intermediate variables that are only used once for the return. Confidence: 0.6
- When a cached data property may not be populated yet, decide via null-coalesced defaults (e.g., `(array) ( $this->type->branches ?? [] )`) and `is_string()` type checks rather than `property_exists()` probing — the latter is fragile during the data-population phase. Confidence: 0.6
- When implementing a "should we use X" decision, check the actual resource availability (e.g., the cached asset list) rather than a proxy derived from a sentinel default value (e.g., `newest_tag !== '0.0.0'`) that conflates "never fetched" with "doesn't exist". Confidence: 0.7
- For release-asset repos, prefer FAILING the update over a convenience fallback: when no release asset is found, `construct_download_link()` should return `''` (the update fails) rather than falling back to the branch/tag zipball — a `ReleaseAsset` header implies a build step that the plain tag source does not include, so the fallback would install a broken/incorrect update. The user explicitly reversed the zipball fallback in both GitHub and Gitea immediately after it was committed: "default to an empty string that way an update that may be incorrect doesn't happen." This does NOT undo the first-run gate fix — still avoid gating the pre-fetch decision on data that is only populated after the fetch (that blocks first runs). Confidence: 0.9

Confidence: 0.6
- To test whether background/completed work is done (e.g., `waiting_for_background_update()`), check the actual completion bookkeeping (the `ran` key written after a full fetch cycle) rather than cache emptiness — `empty($cache)` conflates "not yet run" with "cache cleared/expired/partial failed fetch". Align method names and comments with the actual semantics (e.g., "has the background fetch completed?") instead of stale descriptions like "not managed by Git Updater". Managed-ness is a property of the repo object/config (repos are built from installed plugins/themes carrying Git Updater headers and/or injected by the Git Updater Additions companion plugin via the `gu_additions` filter, which supplies headers at runtime from its `git_updater_additions` site option — Plugin.php:142, Theme.php:156, Base.php:709), never of the cache — an empty cache just means "not yet fetched", and the not-managed path still works only because a non-managed repo (e.g., a slug missing from config → `false`) can never have a cache row. One consequence: `ran` is only written inside the successful `get_remote_info()` branch (Base.php:333), so a persistently-failing repo (bad token, removed repo, wrong URI) never receives `ran` and stays "waiting" forever — perpetually queued to cron instead of direct-fetched, and blocking `unset_stale_options()` via the any-repo-waiting `$repo = null` path (Settings.php:548). Confidence: 0.7

The user explicitly raised this ("If we choose fail-closed we must consider the other API plugins") before any fail-closed token policy was designed. Confidence: 0.85
