# Testing
- The test suite is run against the latest WordPress release (e.g., WordPress 7.1+), not a pinned version, so new WP point releases can surface new test failures — the user directs "run test suite and fix any issues. Now running latest wordpress release" and expects the suite made green against the newly-released WP. When new WP versions add core registries/behavior, adopt the resulting testing patterns (below) rather than dismissing the failure as a broken environment. Confidence: 0.60
- WordPress 7.1 hooks `_wp_register_default_icon_collections` and `_wp_register_default_icons` onto `init` (default-filters.php); both call singletons that throw a "doing it wrong"-style notice ("Icon collection is already registered" / "Icon is already registered") when re-invoked. Because the test bootstrap already fires `init` once (registering the `core` collection and all `core/*` icons), any test that calls `do_action('init')` a second time triggers these notices, which `WP_UnitTestCase` fails on. Fix follows the same pattern as the `WP_Block_Bindings_Registry` gotcha: snapshot registered icon-collection slugs in `set_up()` via `wp_list_pluck( WP_Icon_Collections_Registry::get_instance()->get_all_registered(), 'slug' )`, unregister ALL collections (each `wp_unregister_icon_collection( $slug )`, which cascades to that collection's icons) immediately before `do_action('init')` in the test body, and in `tear_down()` unregister only collections not present in the snapshot — all guarded by `class_exists( 'WP_Icon_Collections_Registry' )` for older-WP compatibility. Document the new gotcha in `docs/claude-testing-gotchas.md` alongside the block-bindings one. Confidence: 0.65
- Coverage reports are produced as `coverage/clover.xml` (single-site) and `coverage/clover-multisite.xml` (multisite); inspect `count="0"` lines in these files to locate uncovered statements. Confidence: 0.85

Confidence: 0.85
- Test on both single-site and multisite WordPress configurations before committing test changes — the user explicitly probes whether test changes (e.g., capability-gate test setups) hold up on multisite, so run the affected suites in both environments. Confidence: 0.75
- When multisite test failures appear, verify whether they are pre-existing/order-dependent before blaming the change: run the failing class in isolation with your changes (`vendor/bin/phpunit --filter <Class>` inside the tests-cli container), and if it passes there, run the full multisite suite again fresh — a transient `git stash`/`git stash pop` mid-suite can pollute test state and produce order-dependent `WPDieException: Forbidden` capability failures that vanish on a clean rerun (e.g., `Test_Repo_List_Table_Extended` failures under multisite). Do not bisect your diff for unrelated failures until you have confirmed they reproduce on a clean run. Confidence: 0.70
- Remove dead code (unused methods) when they are no longer called, and update tests accordingly — this extends to test-side dead code left behind by a storage migration: test helpers that are defined but never called and write to an option scheme production no longer reads (e.g., `seed_complete_cache()` writing `ran` to a `ghu-` site option), `delete_site_option( 'ghu-...' )` cleanup calls that are silent no-ops, and option seeds that are never consumed — and where a test genuinely needs to seed data, re-point the seeding at the new storage (e.g., the cache table) instead of the obsolete option. - Maintain `coverage-exclude.json` when triaging uncovered lines: add entries for lines that legitimately cannot be covered, and the file is consulted during coverage checks to skip those lines when measuring coverage completeness. The file uses exactly two top-level keys — `singlesite` and `multisite` — each mapping file paths to arrays of line numbers; do not invent other keys (e.g., `unreachable`). When unsure of the format, read the consumer script (`coverage-check.php`) rather than guessing. Confidence: 0.85

When a coverage summary flags a line, triage between a real gap and a stale exclusion by checking whether the listed line is still a statement in the current source, whether a passing test covers it under the right env (`WP_MULTISITE=1`), and whether the report is fresh — then update the entry to the current line number rather than leaving a dead entry.
