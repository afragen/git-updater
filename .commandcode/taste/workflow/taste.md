# Workflow
- When a fix is proposed, the user challenges its real value with terse questions (e.g., "Does fixing D1 actually solve a problem other than all the API request data needs to be re-collected?"). They expect an honest severity assessment that distinguishes trivially re-collectable cache data from genuine state loss (e.g., persisted branch selections, error-backoff state whose reset causes an API burst), and an explicit willingness to skip/deprioritize the fix if its only benefit is re-collection. Confidence: 0.75
- When a performance optimization is proposed, the user challenges it with a cost/benefit question ("revert the M3, not sure the complication is worth it. How much time would it actually save?") and expects an honest, quantified estimate of real-world time saved (e.g., 2 sub-millisecond indexed lookups per repo ≈ single-digit ms per page load at realistic repo counts), not a theoretical query-count reduction — and will direct reverting a change whose added complexity (e.g., cache invalidation) outweighs the negligible gain. Confidence: 0.85
- When a code change removes a workaround that existed to mitigate a documented platform limitation (e.g., the drop-before-dbDelta install because "dbDelta is unreliable for adding new elements"), the user probes with a terse question ("What about the note re: dbDelta being unreliable for adding new elements?") and expects the new design to explicitly handle the underlying limitation rather than silently dropping the safeguard — verify the claim against source, then incorporate a mitigation (e.g., schema-versioned migration that runs dbDelta and verifies the expected columns via DESCRIBE, dropping only as a last resort). Confidence: 0.75
- Commit changes after completing each distinct work phase. Confidence: 0.90
- Do not publish packages to npm; leave publishing for the user to handle manually. Confidence: 0.65
- Run tests before committing changes to verify nothing is broken. Confidence: 0.80
- Use tiered approach: address High priority issues first, then Medium, then Low. Confidence: 0.80
- When taste files are modified, omit them from any commit rather than reverting them with git checkout. Confidence: 0.70
- Taste files are always committed ONLY together with other taste files — a commit containing taste file changes must not also include code/test changes, even in repos where `.commandcode/taste/` is tracked (e.g., git-updater). The user stated this as an explicit rule: "Taste file will always be committed ONLY with other taste files." This overrides any prior repo-dependent behavior of bundling taste files into code commits. Confidence: 0.97
- Create a CHANGES.md entry before committing, unless the user explicitly specifies to commit without changelog entries. Confidence: 0.85
- Document new user-visible behavior with a concise `[unreleased]` bullet in CHANGES.md (single line, lowercase, covering the change; e.g., email notification + reminder cadence). Confidence: 0.75
- Verify a plan before implementation: the user reviews plans carefully and points out logic flaws (e.g., a dedupe guard that can never trigger because the flag is always cleared first), so re-check control flow against the actual code before finalizing. Confidence: 0.80
- Keep plan documents under `~/.commandcode/plans/` current with the latest understanding: when a follow-up discussion clarifies or corrects the semantics after a plan was written — even after implementation is done and verified — update the plan to document the refined model (e.g., the "managed-ness comes from the repo object/config, never the cache" model for `waiting_for_background_update()`, including the `gu_additions` path) rather than leaving it describing the superseded framing. The user prompts this with terse questions like "Do we need to update the plan for waiting_for_background_update()?" and approves the documentation-only revision without code changes. Confidence: 0.7
- CHANGES.md entries should be concise — a short single-line summary of the change rather than a long description. Confidence: 0.80
- Use Apple Container and opossum via wp-env-macos for container operations instead of running Docker directly. Confidence: 0.95
- The wp-env binary was renamed from `wp-env-opossum` to `wp-env-macos` — the old name no longer exists; use `./node_modules/.bin/wp-env-macos` for both tests (`test`) and coverage checks (`coverage:check --exclude coverage-exclude.json`). The user corrected the assistant when it looked for the renamed binary. Confidence: 0.85
- When the same bug affects multiple satellite plugin repos with an identical root cause, apply the same fix uniformly across every affected repo, and commit each repo separately using the same commit message (e.g., loop over the repos). Confidence: 0.80
- After a fix lands in the main repo's shared trait/logic (e.g., `use_release_asset()` in GU_Trait, inherited by all host API classes), audit each satellite API repo's parallel `construct_download_link()` and apply the fix only where the identical defect exists: Gitea had the same `return ''` dead-link pattern and was fixed; GitLab (CI-job artifact fallback) and Bitbucket (returns a link or falsy) needed no change; Bitbucket Server has no release-asset block. Verify each host's return shape before changing it. Confidence: 0.7
- Write commit messages with a concise summary line and a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer; for larger changes include a body paragraph explaining the root cause and a bulleted list of the changes — small, focused fixes can be a one-line summary plus the trailer. Confidence: 0.70
- Once the root cause is understood and a fix is identified, proceed to implementation promptly rather than continuing to investigate; the user nudges when analysis drags on or when nothing visibly happens (e.g., an interrupted file write leaves no deliverable on disk). Confidence: 0.82
- After adding or changing a Composer dependency in `composer.json`, also update `composer.lock` (e.g., `composer update <package> --with-dependencies --no-interaction`) so the committed lock file stays in sync and CI installs the new dependency. Confidence: 0.65
- In the API plugin repos (e.g., git-updater-bitbucket, git-updater-gitea, git-updater-gitlab), `.gitignore` should use an allowlist approach for `vendor/`: ignore everything except the minimal paths needed for CI autoloading — track only `vendor/composer` and `vendor/autoload.php` (`vendor/bin` and `vendor/afragen/singleton` are NOT tracked). Do not add per-package ignore entries for each installed dev dependency. The user explicitly rejected a plan that would fully gitignore `vendor/` for these repos — the committed Composer autoloader must stay there. (git-updater-gist is an exception: it fully gitignores `/vendor/` and untracks it, because it uses a custom PSR-4 autoloader instead of the committed Composer autoloader.) Confidence: 0.85
- For git-updater-gist, which uses a custom PSR-4 autoloader (`autoloader.php`) that loads the plugin's own `src/` classes and loads `vendor/autoload.php` only when present, `vendor/` is fully gitignored (`/vendor/`) and untracked via `git rm -r --cached`; the committed Composer autoloader is not needed. The user approved this approach. Confidence: 0.70
- Use the current stable major version of GitHub Actions in workflow files and plans (e.g., `actions/checkout@v7`, not `@v4`); the user tracks latest action releases and corrected a plan that used an outdated version. Verify the current release when unsure. Confidence: 0.80
- When asked to execute an already-approved plan saved under `~/.commandcode/plans/`, proceed directly to implementation — do not enter plan mode and do not re-present the plan via exit_plan_mode; read the plan file first, then implement it step by step. The user repeatedly issues the terse directive "implement plan" for this. Confidence: 0.85
- When the user configures the tool via settings.json (e.g., `permissions.additionalDirectories`), they want an observable way to verify the configuration is actually applied — a command that displays current state, or a concrete behavioral test — rather than taking the settings at face value; explain both the mechanism and how to confirm it. The user will actively test any suggested verification command and report back if it does not reflect the configured state, so verify against the source that the command actually surfaces the state before recommending it (e.g., `/status` and `/add-dir` do not display settings-configured dirs). Confidence: 0.80
- When a built-in Command Code command lacks a feature they need (e.g., no command displays settings-configured `additionalDirectories`), the user prefers to extend the tool itself by building a custom slash command via the official mod system (mod-builder skill) rather than working around the gap externally. Confidence: 0.60
- After a file write that was supposed to create a deliverable (e.g., a mod file), verify it actually landed on disk (e.g., `ls` the target directory) rather than assuming success — interrupted writes can silently fail and the user will report that "nothing is happening." Confidence: 0.70
- Missing Docker does not mean the test suite cannot run — this project's tests run via `wp-env-macos` (Apple container + opossum), not Docker. Run the fast local checks first (`vendor/bin/phpcs`, `vendor/bin/phpstan analyse` on changed files, `php -l`), then check the environment is up (`wp-env-macos ps`, e.g., `tests-cli` running) and run the full suite with `node_modules/.bin/wp-env-macos test` rather than concluding the suite is unrunnable. Confidence: 0.65
- When asked to "check <method> with the preceding changes" (e.g., "Check get_repo_plugin_meta() with the preceding changes") after a code change, trace how the changed helper interacts with every caller — including the failure path — and report any behavioral regressions the change introduces (e.g., `waiting_for_background_update()`'s `ran` check means a persistently-failing repo is now queued to cron forever and blocks `unset_stale_options()`), rather than just confirming the tests pass. Confidence: 0.7
- Do not make code changes beyond the explicit request: when the user declines an options or design question (e.g., a retry guard for a regression, or how to gate unauthenticated REST endpoints serving the git-updater-lite client), leave the code as-is and surface the finding in the summary for a later decision rather than proceeding with the recommended change unrequested — this includes declining to apply a security "fix" whose only effect would be to break legitimate product flows (e.g., anonymous endpoints backed by HMAC-signed, short-lived download tokens are the intended trust boundary). Confidence: 0.7
- When the user requests a review/audit of where data is stored (e.g., "ensure all repository data is stored in tables and update_site_option only used for general data"), deliver a complete categorized inventory — every `update_site_option` key and its purpose vs. every table column — and flag any violations of the stated principle, including legacy writes only referenced by tests, each with a concrete migration recommendation (code snippet + tests to update). Confidence: 0.7
- When the user asks to "run a audits" for security, database security, memory management, DRY, CRUD, or similar — explicitly including "and anything else you can think of" — they expect a comprehensive multi-dimensional audit covering every named category plus any additional relevant dimensions the assistant can identify, with every finding verified against the actual code, cited as file:line, rated by severity, and delivered as a structured report that also notes what is properly secured and ends with a prioritized fix list. Confidence: 0.7
- When the user asks "Is there any other code that has the same issue?" after a defect is found, they expect a systematic audit for the same defect class across all files of the same category — not just source: also compare documentation, CHANGES.md history, and translation `.pot` files between the two sides (e.g., a branch based on an older snapshot silently missing newer sections/entries the mainline has) — and report the full list before continuing the main task. Confidence: 0.7
- During a rebase/merge, resolve CHANGES.md conflicts as purely additive history: always keep the full mainline (newer) version including every version-release section (e.g., the 14.x history), and only append the incoming branch's new `[unreleased]` bullets — never adopt the feature branch's older file structure, which drops release history the mainline already has. Confidence: 0.8
- During a rebase, when taste files conflict, keep the mainline branch's (dev's) taste files rather than the feature branch's versions — "keep all taste files from dev during the rebase." Confidence: 0.7
- When the user states the intent behind existing behavior the assistant flagged as a bug (e.g., "The desire with running this in GU_Upgrade is that all repo data that is obtained via API request is removed so another API request may occur"), treat the behavior as intentional design and reframe the fix to preserve that intent — refine the behavior (e.g., a targeted clear of API-derived columns instead of a full table drop) rather than reverting or removing it; confirm with the user which data must survive before implementing. Confidence: 0.8
- Prefers keeping small, tested, harmless code (e.g., dead CRUD methods `get_all_rows`/`modify_table`/`update_entry`/`delete_entry` with no production callers) over removing it when removal would churn test files and touch the abstract class contract for zero production behavior change — dead-code removal is only worth it when the churn is minimal; confirm before proceeding. Confidence: 0.7
