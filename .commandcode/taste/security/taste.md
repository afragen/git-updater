# Security
- When a security fix is proposed (e.g., S4 token scoping in `Basic_Auth_Loader`), the user asks for both the fix approach AND the threat model ("explain how you would fix S4 and how a malicious/compromised repo header could occur") — they want the concrete attack vectors spelled out (how the exploit could actually happen in the current code, e.g., the "Enterprise" branch sending a GitHub PAT to any host named in a repo header) before implementation, not just the patch; ground the explanation in the actual source. Confidence: 0.65
- Proactively offer security reviews for codebase changes. Confidence: 0.85
- Admin settings save handlers must verify capability in addition to nonce verification — a nonce alone lets a low-privilege authenticated user with a minted nonce alter site settings, tokens, or config lists; apply the capability check to every POST save handler (e.g., `Settings::update_settings()`, `Additions/Settings`, `Lite_Domains`). The check must work in BOTH single-site and multisite: use the established dual-context pattern `current_user_can( is_multisite() ? 'manage_network_options' : 'manage_options' )` for network-wide settings, since `manage_options` alone is wrong on multisite. The user explicitly required this ("capabilities checks must work for both single site and multisite"). Confidence: 0.9
- When the user asks to "explain the security issues in detail" after a list of findings has been verified, they expect a thorough, source-grounded breakdown rather than a summary or restatement: each finding traced to exact `file:line`, its root cause, the concrete attack chain, and an explicit live-vs-already-fixed status verified against the working tree AND git history (naming the fixing commits). Confidence: 0.55
- When the user asks whether one security control makes another unnecessary (e.g., "if we run the Install create_form() through a nonce check is it necessary to use an allow-list?" / "if we validate against a nonce do we even need an allow-list?"), do NOT confirm the redundancy — separate the distinct properties each control protects and state which is which. A nonce (`wp_verify_nonce`) is a CSRF/intent control that proves who is asking for a named action; an allow-list is a destination control over where the server sends a request and, critically, where it attaches a stored PAT — a legitimately nonced request to an attacker-chosen URL still leaks the token. Also answer the follow-up "how would I not send an Authorization: Bearer header?" with the concrete mechanism (host gate on credential attachment), not just a restatement of the risk. Confidence: 0.7
- Attach stored credentials destination-scoped and fail-closed: make the decision from the resolved request host — never from a client-supplied field such as `$_POST['git_updater_api']` alone — and send no `Authorization` header (skipping the auth-header filter) when the host is not in that provider's host set. When a trust decision is needed, re-derive the host server-side from the posted URI (`wp_parse_url( $url, PHP_URL_HOST )`) rather than trusting a separately posted hostname or an inferred value. Confidence: 0.7
- When the user hands over an external audit report (e.g., a wpregistry.io finding URL) and asks to "determine which are still outstanding or necessary to fix," triage BEFORE planning: verify every finding against the current working tree and the fixing commits already landed, classify each (Fixed / Partially fixed / Addressed-by-design / Outstanding), and present the status table first — then build fixes only for the genuinely outstanding items, noting explicitly when a finding is a deliberate design decision the user already settled rather than a real defect. Confidence: 0.6
- Scope audit remediation to the project's own code: findings in the Freemius SDK are ignored entirely ("Ignore issues related to Freemius" — it is a third-party commercial SDK), and findings in vendored third-party libraries (e.g., the vendored Afragen libraries) are out of in-repo scope — those are fixed upstream in their own sibling repos and the composer pin bumped, rather than patching the vendored copy. Confidence: 0.6
- When a proposed security hardening's marginal benefit is questionable, the user wants an explicit cost/benefit framing rather than an asserted recommendation ("that deserves an explicit cost/benefit, not an assertion"): lay out the leave-alone (+ document) option vs the implement option side by side (a comparison table and an honest "bottom line" of what each actually buys), state the conditions under which the cheap option is defensible, and give a recommendation — do not present the hardening as obviously correct. Confidence: 0.55
- When selecting a security mechanism, prefer the simplest primitive that gives equivalent protection under the real transport: over TLS with an already-short-lived download URL, a static per-slug bearer key compared with `hash_equals` is preferred over HMAC+timestamp (no timestamp window, skew handling, or replay machinery), and a self-asserted header that a real credential supersedes is removed rather than kept. The user picked "per-slug bearer key" over the previously approved HMAC design (asking "Is this the most efficient and secure solution?" and accepting "much less code for equivalent protection"). Confidence: 0.65
- Avoid requiring operators to hand-provision secrets into client code or config (a filter, a `GIT_UPDATER_*` constant, wp-config): prefer the client self-generating its credential into a client-side option with a one-time server-side admin approval (pending → approve/revoke), so no secret is typed into code and rotation/revocation stays a server-side action. The user asked "Can this be secured without the client entering a filter or constant?" and accepted the self-generate + approve-once flow. Confidence: 0.6
