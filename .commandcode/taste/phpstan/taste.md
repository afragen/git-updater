# Phpstan
- When fixing PHPStan return type errors, update the `@return` docblock to match the actual return type of the underlying method call, instead of changing the calling code's return behavior. Confidence: 0.75
- When adding new error handling or authentication recovery logic, extract complex inline sections into focused, well-named protected/private helper methods (e.g., `should_attempt_token_refresh()`, `has_bad_credentials_message()`, `maybe_refresh_token_and_retry()`) to improve readability, testability, and separation of concerns. Confidence: 0.90
- For string matching of error messages from external services, use case-insensitive comparison (e.g., `stripos()`) to be robust against provider variations. Confidence: 0.90
- When implementing automatic retry mechanisms for API authentication, trigger token refresh on HTTP 401/403 OR when the response body contains auth error indicators (like "Bad Credentials") on 200 or 4xx codes, but never retry on 5xx server errors. Confidence: 0.85
- PHPStan must stay fully clean (0 errors) across the whole project, and the code must remain compatible with the plugin's PHP 8.0 floor. When PHPStan flags a language construct as unsupported below the floor (e.g., `final protected const` inside a trait is PHP 8.2-only), convert the construct to the PHP-8.0-compatible equivalent (a `final protected static function` returning the value) and update all call sites — do not raise the PHP floor or suppress the error. The codebase documents this exact pattern: "Declared as a method (not a trait constant) because PHPStan flags constants inside traits.". Confidence: 0.70
- When PHPStan (level 6) flags a redundant guard — a condition whose right-hand side it knows is always true, e.g. `isset( $grants[ $slug ] ) && is_array( $grants[ $slug ] )` when the getter is typed to return an array of arrays — fix it by SIMPLIFYING the code (e.g. `$grants[ $slug ] ?? []`) rather than adding a baseline entry, `@phpstan-ignore`, or other suppression; keep the analysis clean by removing the redundancy. The user's terse "test phpstan and fix issues" means run PHPStan, resolve every reported error by the minimal code change, and re-verify. Confidence: 0.65
- When PHPStan flags a `mixed` value used in a strict `in_array($x, [...], true)` (e.g., a field read from a decoded `json_decode(..., true)` body via `$body['error'] ?? ''`), cast it to a concrete scalar first (`(string) ( $body['error'] ?? '' )`) so the strict third arg isn't evaluated against a `mixed` type — PHPStan will not accept the bare `mixed` and the true/strict use is what triggers the complaint. Confidence: 0.65
- Prefer an inline `function_exists()` guard over a `phpstan-baseline.neon` entry when calling a WordPress function missing from the installed stubs (e.g. `wp_get_icon()`, `wp_register_icon()`): the guard satisfies PHPStan and doubles as the runtime back-compat check for older WordPress. If a baseline entry was added for such a call and later stops matching (PHPStan reports it as unmatched), delete the entry instead of leaving a stale ignore. Confidence: 0.6
